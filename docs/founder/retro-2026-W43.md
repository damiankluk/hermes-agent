## Verified failures and root causes

1. Reclamation and stale ownership remained a material delivery cost. Ten runs were reclaimed; the read-only query showed repeated exact errors such as `stale_lock=hermes-agent-7dbcbdbc94-5r7rt:29` and one `manual_reclaim lock=hermes-agent-865cb769cc-sxnww:36`. This is a dispatcher/lease-health problem, not a worker-quality conclusion. Related current card: `t_98d5b40f`.
2. Block loops were detected 22 times across 12 cards. `t_cb57609b` alone had 6 events; `t_ecef5c4e` had 3. The loop detector is firing, but repeated runs and block events still consume capacity before the card settles.
3. External capability and human-decision prerequisites were mixed into ordinary throughput. Current blocked examples include `t_ecef5c4e` (missing browser/dependency prerequisites), `t_2de95f68` (Lighthouse below the fixed threshold), `t_d05e020b` (missing Cloudflare Access path), and `t_990dab2c` (dependent PR merge). These are correctly blocked, but they should not be interpreted as dispatcher capacity failures.
4. Title-level duplicate work still occurred despite no idempotency-key collisions. The same title was created three times for the WordPress alert (`t_43a483d8`, `t_535fce09`, `t_cb34ec13`) and three times for the Alpha Insight weekly review (`t_c760dea3`, `t_c72a9183`, `t_04855730`). Their keys differed (`infra-watcher-*` and three distinct CEO keys), so the existing guard cannot suppress semantically duplicate producers.
5. Project scope was absent on 35 of 204 new cards. The week query grouped `project_id IS NULL` as 35. This is consistent with the existing project-inheritance/decomposer memory and warrants a regression check, but this report does not claim that every null was erroneous.
